# Release tags are signed with a dedicated SSH key

## Context

`tag-release.yml` pushed annotated but unsigned tags. Issue #356
wants `bin/hostwarden-update` to run `git verify-tag` before it
checks a tag out, which only works without an exception list if
every release tag carries a signature, v1.0.0 included. The tag is
created on a GitHub-hosted runner, so the key has to reach it as
an Actions secret.

## Decision drivers

- Verification in a checkout must need nothing beyond git and
  OpenSSH.
- A leaked CI secret must not compromise a person's own identity.
- A wrong or missing key must stop the release, not ship it
  unsigned.

## Considered options

### SSH key used only for release tags — chosen

`gpg.format=ssh`, an ed25519 key in the repository secret
`RELEASE_SIGNING_KEY`, the public half in `.github/release-signers`
and on the updates page. The runner ships `ssh-keygen`; a checkout
verifies with one allowed-signers line. Against it: GitHub shows
the tag as unverified, since no account owns the key.

### GPG key

Classic signed tags. Against it: a keyring to import on the runner,
and GnuPG plus a trust decision on every verifying checkout, for
nothing an allowed-signers line lacks.

### The maintainer's personal signing key

Tags would show as verified on GitHub. Against it: the maintainer's
own key would sit in an Actions secret, and rotating it after a
leak would touch everything else it signs.

### An organisation secret

Survives a transfer of the repository. Against it: one more scope
to keep narrow, for a secret only one repository uses.

## Decision

A dedicated ed25519 key, generated by the maintainer and stored as
the repository secret `RELEASE_SIGNING_KEY`, signs every release
tag. The workflow verifies each tag against
`.github/release-signers` before pushing it, and fails without one.

## Consequences

A release cannot be cut until the secret is set. Rotating the key
adds the new key to `.github/release-signers` and the updates page
in one pull request before the secret changes, and bounds the old
key's line with `valid-before` instead of removing it, so earlier
tags still verify. A leaked key is removed, since a backdated tag
passes the bound. `.claude/rules/repo-release.md`
→ VERSION carries the constraint; #356 builds the verification on
it.

## Confirmation

The first tag the workflow pushes, v1.0.0, passes
`git verify-tag` against the line on the updates page.
