# Configuration Management

A host can be managed by a configuration management tool — wholly,
in some areas, or not at all — and a change made by hand to what
such a tool owns lasts only until its next run. This file says how
to tell, what to record, and what that changes about working on the
host.

## Never push for one

Do not suggest Ansible or any other tool on your own — not after a
repeated change, not after drift in a fleet audit, not in a
recommendation line. When the user asks whether one would pay off,
answer from what memory holds (how many hosts, how many share a
role) and name the cost as well as the gain.

## Detect

Run the probe below, batched into the activity check's call
(`rules/ssh-connections.md` — one call per logical step):

- on the first connection to a host;
- when the activity check shows Ansible runs (`rules/activity-check.md`
  → Ansible runs) and the host's memory has no `Config management:`
  line;
- while a `Config management: unknown` line is there and this session
  can read what the last one could not;
- when the user says a tool manages the host.

Only Ansible is seen again on later connections, through its journal
entries. Puppet, OpenVox, Chef and Salt are looked for by this probe
alone.

```
echo "##dirs"; ls -ld /etc/ansible/facts.d /root/.ansible \
  /home/*/.ansible /Users/*/.ansible /etc/puppetlabs \
  /usr/local/etc/puppet /etc/chef /etc/cinc /etc/salt \
  /usr/local/etc/salt 2>/dev/null || true
echo "##pull"; { crontab -l 2>/dev/null; cat /etc/crontab \
  /etc/cron.d/* 2>/dev/null; } | grep ansible-pull || true
echo "##units"; systemctl list-unit-files 2>/dev/null \
  | grep -Ei "ansible|puppet|openvox|chef|cinc|salt-minion" || true
```

What the leads mean — none is proof on its own
(`rules/verify-before-reporting.md`):

- `~/.ansible/` in a login user's home is Ansible's remote working
  directory; its modification time says when Ansible last connected
  as that user. `/etc/ansible/facts.d/` holds custom facts.
- The other directories and units belong to the agents of Puppet or
  OpenVox, Chef or Cinc, and Salt (under `/usr/local/etc/` on
  FreeBSD).

Every search ends in `|| true`, because finding nothing is the
normal case and must not read as a failed command. Use the OS's own
service listing where `systemctl` does not exist
(`rules/os/<family>.md`).

**Only on a hit**, or on Ansible runs in the journal, look for the
files the tool writes — they are what the scope question below is
about:

```
grep -rIsHo -m1 -E \
  "Ansible managed|managed by (Puppet|Salt)|Generated by Chef" \
  /etc /usr/local/etc 2>/dev/null | head -n 20 || true
```

`Ansible managed` is the default of Ansible's `ansible_managed`
variable; the others are common template headers. A site can change
or drop any of them.

As a non-root user, `/root`, root's crontab and parts of `/etc` are
unreadable, and `2>/dev/null` makes that look like absence. Run the
probe through `sudo -n sh -c` where sudo is available
(`rules/privilege-escalation.md`). Where it is not, say the check
was partial and record `Config management: unknown (privileged
paths unread, <date>)`, so that a later session with root looks
again.

Nothing found and nothing left unread: say nothing, record nothing.

**Not a lead:**

- On the local machine, `~/.ansible/` belongs to the user running
  Ansible from it, not to Ansible managing it.
- An appliance that uses one of these tools as its own mechanism —
  OpenMediaVault renders its system files from Salt states — is
  governed by its appliance file (`rules/appliance/`).
- Windows hosts are read-only (`rules/os/windows.md`), so nothing
  here changes what Hostwarden does there; the probe is not run.

## Ask once, record

On a hit for a host whose memory has no `Config management:` line,
report the leads — directories with their dates, units, the files
that carry a marker — and ask one question: does this tool manage
the host?

- **Yes, the whole host.**
- **Yes, some areas** — ask which: a service, a directory, a role
  name, in the user's words.
- **No longer** — the markers are left over.
- **Don't know.**

Record the answer in the host's memory:

```markdown
- Config management: ansible
- Config management: ansible (scope: base, nginx)
- Config management: puppet (detected)
- Config management: none (ansible markers stale, 2026-09-22)
```

`detected` stands for "don't know": treat the host as managed wherever
a marker or the tool's directories say so. The `none` line keeps the
question from coming back; ask again only when the activity check
shows Ansible runs after its date, or the user raises it. When the
user takes a host or an area out of a tool, change the line or
remove it; the files stay as they are, and from then on Hostwarden
changes them by hand.

Terraform and OpenTofu leave nothing on a host to detect. Record
them only when the user says so:

```markdown
- Provisioned by: opentofu (~/infra/hosting)
```

## What it changes

- **Reading is unchanged.** Housekeeping, audits and questions work
  as on any other host.
- **A change outside the tool's scope** is made by hand, as on any
  other host. Hosts mix freely: a request that spans several is
  split by their lines, and the report says, per host, which way
  the change went.
- **A change inside it** — a file in a named area or carrying a
  marker, or a package or service the tool manages there — belongs
  in the tool's code, or the tool undoes it. Say so, name the file
  and the change, and let the user decide:
  - **In the tool's code.** For Ansible, Hostwarden can edit the
    user's playbooks and roles on this machine when asked; applying
    them is the user's step. For the other tools the user makes the
    change.
  - **By hand anyway**, only on the user's explicit request, after
    saying when the tool will undo it: at its next run for Ansible,
    within the agent's run interval for Puppet (30 minutes by
    default), Chef and Salt. Record it in the host's memory until
    it is in the code, and name it in the changelog entry:

    ```markdown
    - Not yet in ansible: /etc/nginx/nginx.conf worker_connections 4096 (2026-09-22)
    ```

- **Unsure whether the target is in scope:** ask; never guess it is
  not.
- **Provisioned by Terraform or OpenTofu:** what that code owns —
  a cloud firewall, a DNS record, the instance size — is changed in
  that code, never in the provider's console or command line tool.
  Hostwarden never runs `terraform` or `tofu`; `apply` can replace,
  and so destroy, a server.

## Why only detection for the others

Puppet, OpenVox, Chef and Salt minions pull their configuration on
their own schedule, so a change made in their code reaches every
host without the per-host pipeline (`rules/first-connection.md`)
ever running. Terraform and OpenTofu provision infrastructure
through cloud APIs rather than administer a host, and their state
holds secrets in plain text (`rules/secrets.md`).
