# Configuration Management Leads

Read on the first connection to a host and whenever a trigger under
`rules/config-management.md` → Detect fires: the second probe, what
each lead means, and the question that settles a lead the host's
memory does not account for. `rules/config-management.md` is read
first, on every connection; what it says about batching the probes
and about running them without root holds here too.

## Cron jobs and rendered files

```
p='ansible[-]pull|puppet[ ]apply|chef[-]solo|salt[-]call'
p="$p|cf[-]agent|rudder[ -]agent"
echo "##cm-cron"
crontab -l 2>/dev/null | grep -qE "$p" && echo "crontab of $(id -un)"
grep -lsE "$p" /etc/crontab /etc/cron.d/* /usr/local/etc/cron.d/* \
  2>/dev/null || true
echo "##cm-markers"
find -H /etc /usr/local/etc -type f -size -1024k \
  -exec grep -IsHo -m1 -E \
    "Ansible managed|managed by (Puppet|Salt)|Generated by Chef" \
    {} + 2>/dev/null | head -n 20 || true
```

The cron patterns are the masterless runs — the tool invoked from a
cron job rather than by an agent or from a control machine — and
none of them spells its command out (`AGENTS.md` → Critical Safety
Rules). `/usr/local/etc/cron.d/` is FreeBSD's
(`rules/os/freebsd.md` → Directory Conventions).

What the leads mean — none is proof on its own
(`rules/verify-before-reporting.md`):

- `~/.ansible/` in a login user's home is Ansible's remote working
  directory; its modification time says when Ansible last connected
  as that user. `/etc/ansible/facts.d/` holds custom facts.
- The other directories and units belong to the agents of Puppet or
  OpenVox, Chef or Cinc, Salt (under `/usr/local/etc/` on FreeBSD),
  CFEngine (`/var/cfengine`, with `cf-agent` and `cf-execd` in its
  `bin/`), and Rudder (`/opt/rudder`, which carries a CFEngine agent
  of its own).
- `Ansible managed` is the default of Ansible's `ansible_managed`
  variable; the others are common template headers. A site can
  change or drop any of them, so files without one prove nothing.

Every search ends in `|| true`, because finding nothing is the
normal case and must not read as a failed command. The cron search
prints where the job is, never the line: a pull line can carry a
repository URL with a token in it (`rules/secrets.md`).

`-size -1024k` is what bounds the cost of the marker search, since
`-m1` stops early only in a file that carries a marker and every
other file is read to the end. A rendered file above the cap is
missed; one that large is rare, and such a host shows its tool in
the directories and units anyway. `-H` is not optional: on macOS
`/etc` is a symlink, and without it `find` walks nothing at all and
the search reads as a clean host.

## Ask once, record

On a hit the host's memory does not account for, report the leads —
directories with their dates, units, the files that carry a marker —
and ask one question about the tool that is new: does it manage the
host? A hit is unaccounted for in three ways:

- the memory has no `Config management:` line;
- it has a dismissal the hit outdates — an `unknown` one, a `none`
  line, or a `no <tool>` entry for the tool just found;
- it has a confirmed line that names other tools but not this one.

The third is the one a host grows into: a Puppet agent turns up on a
host recorded as `ansible`, and asking is the whole point. The
answer joins the line rather than replacing it, and a tool the line
records as managing the host is not asked about again.

- **Yes, the whole host.**
- **Yes, some areas** — ask which: a service, a directory, a role
  name, in the user's words.
- **No longer** — the markers are left over.
- **Don't know.**

Record the answer in the host's memory, one entry per tool:

```markdown
- Config management: ansible
- Config management: ansible (scope: base, nginx)
- Config management: puppet (detected)
- Config management: ansible (scope: base), puppet (scope: monitoring)
- Config management: ansible, no puppet (markers stale, 2026-09-22)
- Config management: none (ansible markers stale, 2026-09-22)
```

`detected` stands for "don't know": treat the host as managed wherever
a marker or the tool's directories say so. A `no <tool>` entry, and
the `none` line where no tool is left at all, are what keep the
question from coming back — record a dismissed lead or the same
directory asks again on the next connection, since the probe that
found it runs on every one.

Both carry a date, and neither is permanent. A dismissal covers what
is inert — a directory, a file, a unit that is installed and left
off — and says those were stale on that date. It stops holding as
soon as the probe returns something the date does not explain:

- **An agent service the listing shows as enabled**, whichever
  branch found it — on FreeBSD, a `<tool>_enable="YES"` line. That
  is not a leftover, and no service listing prints a date to compare
  against, so an enabled agent outdates a dismissal by itself — the
  one case where the dates do not decide.
- **Ansible runs in the journal** after that date
  (`rules/activity-check.md` → Ansible runs).
- **A directory or file whose own date is later**, as `ls -ld`
  prints it beside the path.

A host recorded `puppet, no ansible (markers stale, 2026-09-22)`
whose next connection shows Ansible runs is asked again, and so is
one whose dismissed Puppet unit has since been enabled; either way
the entry is replaced by the answer. Otherwise ask again only on one
of the triggers under `rules/config-management.md` → Detect, or
when the user raises it. When the user takes a host or an area out
of a tool, change the line or remove it; the files stay as they
are, and from then on Hostwarden changes them by hand.

Terraform and OpenTofu leave nothing on a host to detect. Record
them only when the user says so:

```markdown
- Provisioned by: opentofu (~/infra/hosting)
```
