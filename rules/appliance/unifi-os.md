# UniFi OS

Base: none
Hardware: vendor

UniFi OS is Ubiquiti's operating system for its consoles: the
gateways that run UniFi Network on the device itself (Dream
Machines, Cloud Gateways, UniFi Express, Dream Router, Dream Wall,
Enterprise Fortress Gateway), the Cloud Keys, and the UniFi NAS
models, which run UniFi Drive. It is Debian underneath, but no
family file applies: Ubiquiti owns the packages, the firewall, the
network configuration and sshd. **Hostwarden reads over SSH and
changes the network only through the UniFi applications**, which
configure the console and every device it has adopted. Where
`AGENTS.md` or a baseline expects something a Linux server has (a
package manager, a host firewall, automatic security updates,
`sudo`), this file says what to check instead.

Adopted devices — access points, switches, other gateways — are
managed through the console. Hostwarden never connects to them over
SSH.

A gateway is usually the network's only way out. A mistake here cuts
off everyone behind it, not just your SSH session.

Sources unless noted: the UniFi help center,
<https://help.ui.com/>, the release notes at
<https://community.ui.com/releases>, and Ubiquiti's firmware index,
<https://fw-update.ubnt.com/api/firmware-latest>. Where Ubiquiti
documents nothing, this file says what to read on the host rather
than what the host contains.

## Version Detection

- **This file is written for UniFi OS 5.x.** On any other major
  release, older or newer, work read-only: say once that
  Hostwarden's UniFi rules are written for 5.x and that paths and
  commands may differ, name the update where one to 5.x exists (see
  Updates), and change nothing on the host, the boot scripts
  included. The UniFi Express (`UX`) is still on the 4.x line; it
  gets the same read-only treatment until Ubiquiti moves it.
- `ubnt-device-info firmware` prints the UniFi OS version,
  `ubnt-device-info model` the model's name.
- The applications have versions of their own and update apart from
  the OS. Read them in the call after the probe with
  `dpkg-query -W -f '${db:Status-Abbrev} ${Package} ${Version}\n'
  'unifi*' 'uos*'`; only a line that starts `ii` is installed, `rc`
  is a removed application whose configuration is still there.
  UniFi Network is the package `unifi`. The Debian
  release underneath is the os-release `VERSION_ID` from the probe;
  it says how Debian's tools behave, never that Debian's rules
  apply.
- Record in server memory:
  `Appliance: UniFi OS <version>, <model>` and the applications with
  their versions, e.g. `Apps: Network 10.6.106`. A console without
  UniFi Network (a UNAS, a Cloud Key running only Protect) records
  what it has.

## Access and Shell

- **SSH is off by default.** The user enables it under Settings >
  Control Plane > Console > SSH and sets root's password there.
  Ubiquiti advises SSH only when support asks for it.
- **root is the only login.** Every session runs as root, so the
  least-privilege care `AGENTS.md` asks of commands is the only
  limit. There is no `sudo` to probe and no unprivileged mode.
- **Keys do not survive a firmware update on their own.** UniFi OS
  has no setting for the console's own SSH keys, and root's
  `authorized_keys` lies outside `/data` (see Configuration Model →
  Persistence). Without a key Hostwarden cannot log in
  (`BatchMode=yes`): a key lost in an update is the cause to check
  first when SSH refuses the login after one
  (`rules/ssh-unreachable.md`).
- **Setting up the key is the user's step.** The SSH taboo in
  `AGENTS.md` keeps Hostwarden away from `authorized_keys`, and the
  first login needs root's password. The user runs, from their
  workstation:

  ```bash operator
  ssh-copy-id root@<console>
  ```

  and, to keep the key across updates, stores it on the console
  under `/data` and lets a boot script put it back. With
  unifi-on-boot installed (see Boot Scripts), the upstream example
  `15-add-root-ssh-keys.sh` from
  <https://github.com/unifi-utilities/unifi-common/tree/main/examples>
  reads the keys from `/data/on_boot.d/settings/ssh/authorized_keys`.
  Hostwarden names these steps and runs none of them.
- **Device SSH is a different setting.** Settings > System >
  Advanced > Device Authentication sets the SSH login and keys of
  the adopted devices, not of the console.
- sshd's configuration is generated by UniFi OS and falls under the
  SSH taboo: read only. Whether the SSH server is OpenSSH or dropbear
  differs between releases, and both binaries can be installed while
  only one serves: the daemon behind the port is the one that
  answers, so read the listener rather than the binaries —
  `ss -tlnp | awk '$4 ~ /:22$/'`, with the port from server memory
  where it is not 22. The local address field ends in the port, and
  an address in front of it (`0.0.0.0:22`) would defeat a
  whole-word `grep`. Server memory records the daemon as
  `SSH server: openssh` or `dropbear`.

## What Does Not Apply

- **Packages.** Never `apt-get install`, `upgrade` or
  `dist-upgrade`, and never add a source under `/etc/apt`. Ubiquiti
  ships the packages as part of the firmware, an update wipes what
  apt added, and an upgrade of Debian packages can break the
  applications. Queries (`dpkg -l`, `dpkg-query`) are fine.
- **Host firewall** and **automatic security updates**: see Firewall
  and Updates.
- **Accounts.** Admins and users belong to UniFi OS (Settings >
  Admins & Users), not to `/etc/passwd`. Never `useradd`, `usermod`
  or `passwd`.
- **Containers.** Where a release uses containers internally, they
  are Ubiquiti's. Never start, stop or change them.

## Configuration Model

- **The applications own the configuration.** UniFi Network keeps
  the network's configuration in its database and provisions the
  gateway and every adopted device from it. Interfaces, VLANs,
  routes, DHCP and DNS are its settings; the service that applies
  them keeps its state under `/data/udapi-config/`. Never edit it or
  the database, and never change an interface with `ip` or
  `ifconfig`: the next provisioning overwrites a hand edit, or it
  survives until an update and then silently is not there.
- **Changes go through the application**: its web UI or its local
  API (see Network API). Give the user the exact menu path and
  values. A change of the network's configuration names the sites
  and devices it reaches, since one setting provisions many
  devices.
- **On the console itself, over SSH**, the only thing that changes
  is the boot scripts under `/data/on_boot.d` (see Boot Scripts).
  Every change there is a config edit (`rules/backups.md`); ask
  first and show it.
- **Persistence.** A firmware update replaces the system and keeps
  `/data`; `/usr`, `/var` and anything apt installed are gone. The
  backup directory is `/data/hostwarden-backups/`.
- Never run a factory reset, whatever tool offers it, and never
  restore a backup without an explicit request; a restore is the
  user's step in the UI.

## Network API

SSH shows the console; the network's configuration — sites, devices,
clients, networks, Wi-Fi, firewall — is read and changed through
UniFi Network's local API, the way `rules/appliance-api.md`
describes. Over SSH is the default path, against `127.0.0.1`. Only
the local API is used; the cloud's Site Manager API and its
connector are not part of Hostwarden.

### Accounts

The user creates each admin in UniFi OS under Settings > Admins &
Users > Create New Admin, with **Restrict to local access only** on
(no UI account, no cloud login, no MFA prompt for a script) and
every application other than Network set to None, OS settings
included
(<https://help.ui.com/hc/en-us/articles/28692158912279-Adding-Admins-in-UniFi>).

- **Read: an admin `api-read`** with Network set to **View Only**.
  Ubiquiti's API keys have no read-only scope, and a View Only admin
  may not be offered a key at all, so this admin logs in with its
  password. File `unifi-ro.json`, one line:
  `{"username": "api-read", "password": "<password>"}`.
- **Write, only where the user asked for write access: an admin
  `api-write`** with Network set to **Full Management**, or to a
  custom role that covers only what Hostwarden is meant to change.
  Signed in as that admin, the user creates an API key on UniFi
  Network's Integrations page (its place in the
  menu moves between releases; it is named Integrations or API
  Keys). File `unifi-rw.header`, one line: `X-API-KEY: <key>`. The
  key is shown once; a lost key is deleted and a new one created.
- **Reads that only the key reaches** — every read on a console in
  a UniFi Fabric, which accepts no password login
  (<https://github.com/Art-of-WiFi/UniFi-API-client>), and the
  Integration API everywhere — use the write key only when the user
  agrees to that for this console, recorded as
  `API key reads: allowed`. Without it, name what could not be read.
- In server memory:
  ```
  API read: api-read (View Only), ~/hostwarden-keys/<console>/unifi-ro.json
  API write: api-write (Full Management), ~/hostwarden-keys/<console>/unifi-rw.header
  ```

### Reading

- A task's reads over SSH with the read admin, in one call:

  ```
  ssh … root@<console> 'umask 077; j=$(mktemp); trap "rm -f $j" EXIT;
    curl -fsSk -c "$j" -o /dev/null -H "Content-Type: application/json" \
      --data @- https://127.0.0.1/api/auth/login || exit 1
    b=https://127.0.0.1/proxy/network/api/s/default
    curl -sSk -b "$j" -w "\n{\"@\": \"health\", \"code\": %{http_code}}\n" \
      "$b/stat/health"
    curl -sSk -b "$j" -w "\n{\"@\": \"device\", \"code\": %{http_code}}\n" \
      "$b/stat/device"' \
    < ~/hostwarden-keys/<console>/unifi-ro.json | jq …
  ```

  Only the login reads stdin, so each endpoint may have its own
  `curl -b "$j"`. A key-authenticated read is one `curl -H @-` with
  every URL after it (`rules/appliance-api.md` → Reading).

- Secret fields: add `^x_` to the filter's pattern — the classic
  API keeps its secrets in `x_` fields (`x_passphrase`,
  `x_password`, the VPN keys). For housekeeping, project
  `.data[] | {name, model, state, upgradable, version}` for devices
  and `.data[] | {subsystem, status}` for health.
- The endpoints the read admin reaches are the classic API under
  `/proxy/network/api/s/<site>/` — `stat/health`, `stat/device`,
  `stat/sta` (connected clients), `stat/sysinfo`, `rest/networkconf`,
  `rest/wlanconf`, `rest/portforward`, `rest/firewallrule`,
  `rest/firewallgroup`, `rest/routing` — and
  `/proxy/network/api/self/sites` for the sites (`<site>` is each
  site's `name`; the first is `default`). Ubiquiti documents none of
  them; they come from the clients that use them (aiounifi,
  go-unifi) and change between releases.
- The key, where key reads are allowed, replaces the login and the
  cookie with one `curl -H @-` carrying every URL of the batch and a
  `%{url_effective}` marker, and reaches both the classic API and the
  documented Integration API under `/proxy/network/integration/v1/`
  (`info`, `sites`, and per site `devices`, `clients`, `networks`,
  `wifi/broadcasts`, `firewall/zones`, `firewall/policies`, `wans`,
  `vpn/servers`), whose reference is at
  <https://developer.ui.com/network>, one version per Network
  release.

### Writing

- **Prefer the Integration API**, documented and versioned. It
  writes networks, Wi-Fi broadcasts, firewall zones and policies,
  ACL rules, DNS policies, traffic matching lists and vouchers, and
  it restarts devices and power-cycles PoE ports. For anything else
  the key also writes the classic API; say that it is undocumented
  before using it.
- Name every site and device a change provisions. Provisioning to
  adopted devices takes a while; a device still provisioning when
  the object is read back is not a failure.
- Firewall policies and zones, port forwards and the network or
  VLAN the session comes from are changes that can touch the way in;
  UniFi names no revert for them.
- Device restarts and PoE power cycles interrupt clients: ask each
  time, name the device and what hangs off it.

## Updates

- **Only through UniFi OS.** There is no `unattended-upgrades`.
  Settings > Control Plane > Updates shows the pending OS and
  application updates, the release channel (Official or Early
  Access) and auto-update per console and per application. Site
  Manager's Update Manager does the same for a fleet.
- Never update from the shell. `ubnt-systool fwupdate` exists, and
  Ubiquiti calls it "not an officially supported process" to use
  only at support's request
  (<https://help.ui.com/hc/en-us/articles/204910064-UniFi-Advanced-Updating-Techniques>).
  Hand OS and application updates to the user as UI steps.
- **An OS update reboots the console.** On a gateway everyone
  behind it loses the network until it is back, and adopted devices
  may reprovision. Say so when naming the update.
- Pending OS update: compare `ubnt-device-info firmware` with the
  newest `release` version for the model from a live lookup
  (`rules/version-check.md`). Ubiquiti's firmware index serves it
  read-only, per product — `unifi-dream` for the gateways and
  Express, `unifi-cloudkey`, `unifi-drive` for the NAS models:

  ```
  curl -fsS 'https://fw-update.ubnt.com/api/firmware-latest?filter=eq~~product~~unifi-dream&filter=eq~~channel~~release'
  ```

  Run it from the workstation, not on the console. The `platform`
  field is a short code (`UDMPRO`, `UDRULT`), and
  `ubnt-device-info model` prints the marketing name: match the two
  by the release notes' device list, and where that leaves doubt,
  the Updates page decides. The release notes are at
  <https://community.ui.com/releases>. Application versions are
  compared with their release notes the same way.
- Before an OS update, a recent backup exists (see Backups). Since
  UniFi OS 5.1.12 an application can be reverted to its previous
  version from the Updates page; the OS itself cannot.

## Boot Scripts: unifi-on-boot

UniFi OS runs nothing of the user's at boot. unifi-on-boot
(<https://github.com/unredacted/unifi-on-boot>, Unredacted, GPL-3.0)
is a third-party package that runs every script in `/data/on_boot.d`
at each boot and reinstalls itself after a firmware update. It is
the way to extend a console here: persistent SSH keys, routes, a VPN
client, a cron job. Its predecessor, `udm-boot` from unifi-common
(<https://github.com/unifi-utilities/unifi-common>), runs the same
directory.

- **Detect** in the call after the probe, on the first connection
  and whenever memory has no `Boot scripts:` line, and again in
  housekeeping:
  ```
  dpkg-query -W -f '${db:Status-Abbrev} ${Version}\n' unifi-on-boot
  systemctl is-enabled unifi-on-boot unifi-on-boot-install udm-boot
  systemctl is-active unifi-on-boot
  ls -l /data/on_boot.d
  ```
  Record in server memory:
  `Boot scripts: unifi-on-boot <version>` or `udm-boot`, or none,
  and the scripts by name.
- **Install only on request**: it is a third-party source
  (`AGENTS.md`: official repos only). Look up the newest release
  first (`rules/version-check.md`), download the `.deb` from its
  GitHub release to the workstation, compare its SHA-256 with the
  one GitHub shows for the asset, copy it to `/data`, and install it
  with `dpkg -i`. Remove `udm-boot` first where it is enabled: the
  package's `Conflicts:` cannot see the upstream unit, which dpkg
  does not know, and with both every script runs twice.
- **Switch the shadow sync off right after installing**, before the
  service first runs at the next boot or restart: set
  `SHADOW_ENABLED=false` in `/data/unifi-on-boot/shadow.conf`
  (see Shadow-gateway sync below; a config edit). Leave it on only
  where the user confirms that this console is one of an HA pair and
  names the peer's address, which then goes into `SHADOW_IP`.
- **What it adds**: `/usr/sbin/unifi-on-boot`, the units
  `unifi-on-boot` (runs the scripts) and `unifi-on-boot-install`
  (reinstalls the package from `/data/unifi-on-boot/` after an
  update), and the directories `/data/unifi-on-boot/` and
  `/data/on_boot.d/`.
- **How scripts run.** Top-level regular files in
  `/data/on_boot.d/`, in sorted order: name them with a numeric
  prefix, `10-routes.sh`. An executable file is executed; a
  non-executable `*.sh` is sourced in a subshell under
  `set -euo pipefail`; anything else is skipped silently, as are
  `*~`, `*.bak`, `*.orig`, `*.dpkg-*` and dotfiles. A failing script
  is logged and the next one still runs.
- **A script that writes SSH keys or sshd's configuration** is the
  user's to write (see Access and Shell). Run a new script once by
  hand rather than leave its first run to a reboot.
  `systemctl restart unifi-on-boot` re-runs **every** script, not
  just the new one.
- **Logs**: `journalctl -u unifi-on-boot` and
  `/var/log/unifi-on-boot.log` for the scripts,
  `journalctl -t unifi-on-boot-install` for the reinstall after an
  update.
- **Shadow-gateway sync is on by default.** After the scripts ran,
  unifi-on-boot tries to log in as root to a shadow gateway (the
  second gateway of a pair, by default `169.254.254.3`), mirrors
  `/data/on_boot.d/` there with `rsync --delete`, with host key
  checking switched off, and installs its own package there. Its
  settings are in `/data/unifi-on-boot/shadow.conf`
  (`SHADOW_ENABLED`, `SHADOW_IP`, `SHADOW_USER`).
- **Removing it** takes `dpkg -P unifi-on-boot`. After a plain
  `dpkg -r` the reinstall unit and the saved `.deb` stay behind and
  install the package again at the next boot. `dpkg -P` keeps
  `/data/on_boot.d` with the scripts; name the ones that stop
  running.

## Firewall

- **UniFi Network owns the gateway's firewall.** Since Network 9.0 it
  is zone based (Settings > Security, or the Zone-Based Firewall
  page); older configurations may still carry the classic rules
  until the user migrates them
  (<https://help.ui.com/hc/en-us/articles/115003173168-Zone-Based-Firewalls-in-UniFi>).
- Never add rules with `iptables`, `nft`, `ufw` or `firewalld`: the
  next provisioning replaces them, and a rule that lands first can
  cut off the network.
- Read the effective rules from the application, not from the
  kernel. The kernel ruleset is generated and changes at each
  provisioning; when the question is about one rule on this box,
  read only its chain (`nft list chain …`, or `iptables-save` through
  `grep`), and never base a change on it.
- Rules, port forwards and zones change in the application, after
  asking, and fall under `rules/ssh-safety-net.md` with no revert
  (see Network API → Writing): name what reaches SSH and the UniFi
  OS web UI, and the user applies the change with a second way in
  ready.

## Services and Logs

- Services are systemd units. Ubiquiti documents no unit list, and
  names differ between releases: find the application's units with
  `systemctl list-units --type=service 'unifi*' 'uos*'` before
  naming one.
- **Restart nothing Ubiquiti ships.** Applications restart from the
  UI (Settings > Control Plane > Applications, or the application's
  own settings), and a restart of the Network application on a
  gateway can drop the network for the duration. Ask first, always.
- Logs: `/var/log/messages` on every console; on a gateway also
  `/var/log/dnsmasq.log`, `/var/log/freeradius/radius.log` and
  `/var/log/suricata/suricata.log`
  (<https://help.ui.com/hc/en-us/articles/204959834-Advanced-Logging-Information>).
  The applications log under `/data`; find the files with
  `ls /data/unifi*/logs` rather than assume a path. The support file
  (Settings > Control Plane > Console > Support File) collects them
  for Ubiquiti; it stays with the user.
- `logger -t hostwarden` writes to the journal, which lives under
  `/var`: the activity check reaches back at most to the last
  firmware update (`rules/activity-check.md` → How far back it
  reached).

## Backups

- UniFi OS takes system backups — OS, applications and device
  configuration — to the owner's UI account weekly and before a
  major update, set under Settings > Control Plane > Backups.
  The same page downloads one to keep offline
  (<https://help.ui.com/hc/en-us/articles/360008976393-Backups-and-Migration-in-UniFi>).
- UniFi Network also keeps its own autobackups on the console. The
  path differs between models: the housekeeping call lists
  `/data/unifi/data/backup/autobackup`, and where that is empty,
  `find -H /data /ssd1/.data -maxdepth 6 -path '*/backup/autobackup/*'
  -name '*.unf'` finds it once (a UDM SE keeps it under `/ssd1`);
  record it in server memory.
- A backup holds every credential of the network: Wi-Fi keys, VPN
  keys, admin hashes. It never passes through the session and never
  goes into memory (`rules/secrets.md`); report name, age and size.

## UniFi NAS

On a UNAS the application is UniFi Drive, and the rules above apply
with these changes:

- The disks and their volumes belong to UniFi Drive. The disk
  taboos in `AGENTS.md` cover every drive in it; adding, removing or
  replacing a drive and every volume or share change are the
  user's, in the Drive UI. Hostwarden reads and names the step.
- Read storage with `lsblk`, `df -h` and `cat /proc/mdstat`, and a
  drive's health with the probe in
  `.agents/skills/hostwarden-housekeeping/references/smart.md`.
  What Drive builds its volumes from is not documented; read it off
  the host and report it, never assume one layout.
- A UNAS has no gateway firewall of its own: its exposure is the
  gateway's port forwards and the shares it offers.

## Housekeeping and Audits

**Housekeeping** runs the Linux baseline with these changes:

- Disk Usage, Memory and Swap, System Load, Uptime, Failed systemd
  Units, NTP and Log Anomalies run as written; include `/data` in
  Disk Usage. The journal reaches back at most to the last firmware
  update: say how far.
- Pending Security Updates and Automatic Security Updates: replaced
  by Updates above. A pending OS or application update, auto-update
  off, or the Early Access channel on a production network is the
  finding; a UniFi OS other than 5.x is WARN (see Version Detection).
- Firewall Status: the application's (see Firewall), not checked
  from the shell.
- Backup Presence: replaced by Backups above. No Network autobackup
  in the last week is WARN; cloud backups off, which the user reads
  under Settings > Control Plane > Backups, is WARN.
- SSL/TLS Certificate Expiry, Kernel: Running vs Installed, Ubuntu
  Release and Support, and Critical Services: skipped; they are
  Ubiquiti's.
- A command in these calls that is missing or fails says nothing
  about what it reads: report that check as not run, never as OK.
- Added, in one call: the Detect lines of Boot Scripts, and
  ```
  journalctl -u unifi-on-boot -b -n 20 --no-pager -q
  ls -lt /data/unifi/data/backup/autobackup | head -4
  ```
  Findings: unifi-on-boot installed but not enabled or not active,
  a boot script that failed at the last boot, `udm-boot` and
  unifi-on-boot both enabled; on a UNAS, a degraded array or a drive
  with SMART findings.
- With read access (see Network API), also `stat/health` and
  `stat/device`: a subsystem whose `status` is not `ok`, an adopted
  device that is offline, and a device with `upgradable` true are
  findings; name the device.

**A security audit** runs the security skill with these changes:

- SSH (`references/ssh.md`): by the daemon the listener names (see
  Access and Shell) — with OpenSSH, `sshd -T` as usual; with
  dropbear, its command line in `ps`. Root login with a password is
  how console SSH works and there is no UI option to turn it off:
  not a finding on its own. **SSH reachable from the internet is
  CRITICAL** — a port forward to the console, or a WAN rule that
  passes SSH. SSH on without a reason to have it is INFO.
- Firewall (`references/firewall.md`): replaced by the application's
  rules (see Firewall). With read access they come from the API —
  `rest/portforward` and `rest/firewallrule`, and the zone-based
  `firewall/policies` where key reads are allowed; otherwise the user
  reads them out.
  A port forward or WAN rule to the console's SSH is the CRITICAL
  above; the web UI reachable from the internet directly, not
  through UniFi's remote access, is WARN.
- Listening services (`references/listening-services.md`): as
  written.
- User accounts, Kernel, File permissions, Intrusion prevention:
  skipped; they are Ubiquiti's. Admins instead, read under Settings >
  Admins & Users: an admin not restricted to local access has a UI
  account, and a Super Admin or Owner without MFA is WARN. Name the
  admins, never their mail addresses.
- Boot scripts: list each with what it does; one that fetches and
  runs code from the internet at boot is WARN. unifi-on-boot's
  `SHADOW_ENABLED=true` in `shadow.conf` is WARN on a console that is
  not one of an HA pair, INFO on one that is (see Boot Scripts).

**Fleet audit:** compare on the UniFi OS and application versions,
the release channel and auto-update, SSH state, and unifi-on-boot's
version and shadow sync. A missing `unattended-upgrades` or host
firewall is not drift; the MTA rows are `n/a (UniFi OS)`.
